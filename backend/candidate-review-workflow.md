# MIRA Candidate Review & Promotion Workflow Documentation

## 1. Candidate Lifecycle Architecture

The candidate lifecycle in the **MIRA Decoupled Portfolio Orchestration Engine (DPOE)** manages responses generated by Tier 4 LLM fallback (Gemini) through a multi-stage, human-in-the-loop verification pipeline before any answer can be promoted to the verified canonical FAQ layer (`faq-cache.json`).

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                              CANDIDATE LIFECYCLE PIPELINE                              │
├──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌────────────────┐  ┌──────────────┤
│ 1. GENERATED │─>│  2. STAGED   │─>│  3. AUDITED  │─>│ 4. HUMAN REVIEW│─>│ 5. DECISION  │
│ Tier 4 Fall- │  │ candidate-   │  │ Offline CLI  │  │ Explicit CLI   │  │ PROMOTED /   │
│ back Gemini  │  │ cache.json   │  │ Classifier   │  │ Confirmation   │  │ REJECTED     │
└──────────────┘  └──────────────┘  └──────────────┘  └────────────────┘  └──────────────┘
```

---

## 2. Stage Breakdown

### Stage 1: GENERATED
- **Trigger**: Tier 4 Gemini LLM fallback is invoked when a query misses Layers 1.5, 2, and 3.
- **State**: Response is returned live to the user with grounding disclaimers enforced.

### Stage 2: STAGED
- **Trigger**: Non-blocking staging via `stageCandidate()` in `server.js`.
- **Storage**: `backend/data/candidate-cache.json`
- **Epistemic State**: `"verified": false`, `"source": "gemini-generated-candidate"`.
- **Rule**: Staged candidates can accelerate future similar queries in Layer 3 (8ms latency) carrying `source: "candidate-cache"`, but **MUST NEVER** be treated as ground-truth canonical facts without explicit review.

### Stage 3: AUDITED
- **Tool**: `node backend/scripts/review-candidates.js --stats` or `--dry-run`
- **Classification Categories**:
  - `CANONICAL_DUPLICATE`: Query overlaps directly with an existing canonical FAQ topic.
  - `CANONICAL_SUPPORTED_SYNTHESIS`: Multi-domain synthesis supported by `portfolio.js`.
  - `GUARDRAIL_RESPONSE`: Contains mandatory identity/authority disclosure text.
  - `OUT_OF_SCOPE`: Contains out-of-scope/private data disclaimers.
  - `REQUIRES_REVIEW`: Candidates needing manual inspection.

### Stage 4: HUMAN REVIEW
- **CLI Commands**:
  - Inspect candidates: `node backend/scripts/review-candidates.js --candidate <id>`
  - List reviewable candidates: `node backend/scripts/review-candidates.js --list`

### Stage 5: PROMOTED / REJECTED
- **Promote Command**: `node backend/scripts/review-candidates.js --promote <id>`
- **Reject Command**: `node backend/scripts/review-candidates.js --reject <id>`
- **Safety Enforcement**:
  - `GUARDRAIL_RESPONSE` and `OUT_OF_SCOPE` candidates can **NEVER** be promoted.
  - Automatic promotion is **STRICTLY PROHIBITED** (Automatic Promoted = 0).
  - Promoted entries update `faq-cache.json` atomically (timestamped backup → `.tmp.json` validation → atomic rename).
  - Decision is logged permanently in `backend/data/candidate-promotion-log.json`.

---

## 3. Auditability & Append-Only Log Schema

Every promotion or rejection writes a record to `backend/data/candidate-promotion-log.json`:

```json
{
  "candidateId": "candidate_1786315861870_wam3",
  "originalQuery": "how did Moses acquire his data analysis skills",
  "classification": "CANONICAL_DUPLICATE",
  "decision": "PROMOTED",
  "reviewerDecisionTimestamp": "2026-08-12T17:08:15.578Z",
  "destinationFaqId": "identity-overview",
  "originalProvenance": "gemini-generated-candidate"
}
```

---

## 4. Verification & Safety Guarantees

1. **Production Architecture Untouched**: Runtime files (`server.js`, `system.js`, `portfolio.js`, `cacheMatcher.js`, frontend) are never modified by the CLI tool.
2. **Zero Overwrites**: Promoted candidates append new question variants to existing canonical topics instead of overwriting canonical answers.
3. **Atomic File Operations**: All writes to `faq-cache.json` write to temporary files and perform validation before replacing the production file.
